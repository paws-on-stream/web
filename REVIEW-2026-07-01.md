## 3. Architektur — App Separation

```
core/         → Settings (singleton), DisplayDevice, DisplayLog
streaming/    → Event, Message (+ middleware, middleware tests)
participants/ → Participant
```

### Dependencies

```
core → streaming → participants
```

| Issue | Details |
|-------|---------|
| 🔴 | `core` hängt von `streaming` — inverting "core is foundational" expectation. `DisplayLog` (in `core`) hat FK zu `Message` (in `streaming`). Besser: `core` → `display` rename, oder `DisplayLog` nach `streaming` |
| 🟡 | `streaming` factories import von `participants` — Import coupling in test fixtures |
| 🟢 | `participants` hat zero dependencies — cleanest app, self-contained |

**Verdict:** Apps sind reasonable separated, aber die `core` → `streaming` dependency ist backwards. Nicht blocker, aber sollte für zukünftige Refaktorisierung notiert werden.

## 4. Performance — ~1000 Participants Live

**Annahmen:** 1000 Participants, ~5-10 messages/minute each during peak = 5000-10,000 messages/hour. Live ~12 hours = ~60k-120k messages.

| Concern | Status | Impact |
|---------|--------|--------|
| **No caching** | 🔴 | Every settings fetch hits DB. Display devices polling = N queries/sec |
| **No rate limiting** | 🟡 | 1000 participants spamming = unbounded DB writes |
| **No message TTL / cleanup** | 🟡 | Old messages accumulate (10k-50k rows after convention) |
| **Page size = 20** | ✅ | Reasonable for human consumption |
| **`select_related` on Message** | ✅ | Prevents N+1 for participant + event lookups |
| **No DB connection pooling** | 🟢 | Fine for ~1000 participants |
| **No index on `Message(event, status)`** | 🟡 | Composite index on `[status, created_at]` good, aber per-event queries brauchen `[event, status]` |
| **No pagination on pending/displayed** | ✅ | Sie paginieren — gut |
